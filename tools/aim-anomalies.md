# Нестандартные структуры в AIM-образах

Результат сплошного разбора коллекции образов Агата (`DSKCommander/docs/samples`):
89 файлов `.aim`/`.AIM`, из них **42 уникальных** по содержимому, все размером
2 068 480 байт (160 дорожек × 6464 ячейки × 2 байта). Разбор выполнен скриптом
[`aim_scan.py`](aim_scan.py), порядок секторов — [`aim_order.py`](aim_order.py).

Эталонная структура сектора Агат-840:

```
GAP ($AA) | DESYNC | 95 6A | Volume Track Sector 5A | GAP (3) | DESYNC | 6A 95 | 256 байт | CRC 5A | GAP (29)
```

CRC — восьмибитная сумма данных с добавлением переноса. Дорожка — 21 сектор.
Дамп AIM длиннее оборота на 55…105 ячеек, поэтому последнее поле дорожки
переходит через её начало, а первые ячейки могут оказаться повторным чтением
последних. Это норма, а не аномалия, и при поиске дублей это надо учитывать.

## Сводка

| Образ(ы) | Что найдено |
|---|---|
| VolgoUSN_01…11 (11 шт.) | Эпилог адресного поля `$A5` на дорожках 0–3; особая дорожка 0 |
| OA23, OA27 | Эпилоги `$22`/`$77` на дорожке 0; дорожки без секторов с сигнатурой «KENT» |
| so, copy, vibu35, JOKER | 14 секторов с контрольной суммой XOR вместо суммы Агата |
| CLOCKBADER | Маркер `95 7F "BTa"` на дорожке 7; перемешанный порядок секторов на дорожке 8 |
| MGR4_4 | DESYNC внутри поля данных (дорожка 2, сектор 10) |
| M&S_12, M&S_15 | Команда AIM `$81` вместо `$01` |
| M&S_02…09 (8 шт.) | Хвост каждого длинного GAP'а записан нулями вместо `$AA` |
| M&S_18 | Volume ID меняется от дорожки к дорожке |
| VolgoUSN_12, OA13, M&S_01/0A/10/11/13/14/16/17, TOM11, MarKis | Без отклонений |

**Задвоенных секторов (одинаковый номер дважды на дорожке) не найдено ни одного.**
Проверялись и совпадающие копии, и копии с разными данными или разными эпилогами;
повторное чтение сектора на стыке кольца за дубль не считалось.

## 1. Нестандартный эпилог адресного поля

### VolgoUSN_01…11: `$A5` на дорожках 0–3

66 секторов на каждом из 11 дисков (2 на дорожке 0, по 21 на дорожках 1–3 и один
мусорный) имеют эпилог `$A5` вместо `$5A`. С дорожки 4 и до конца — нормальный `$5A`.
`$A5` — побитовое дополнение `$5A`. Похоже на защиту загрузочной зоны: свой загрузчик
ищет `$A5`, штатный копировщик пишет `$5A`.

```
VolgoUSN_08, дорожка 1:
  [20]00/01 [21]95 [22]6A [23]00 [24]01 [25]00 [26]A5 [27]AA*3 [30]00/01 [31]6A [32]95 ...
                                            vol trk sec  ^^ эпилог
```

`VolgoUSN_12` из того же набора — полностью штатный (эпилог `$5A`, volume `$03` на всём
диске, обычная дорожка 0). Вероятно, снятая защита.

### OA23, OA27: `$22` и `$77` на дорожке 0

У четырёх секторов дорожки 0 эпилог адресного поля `$22`, а эпилог поля данных `$77`.
Пара выбрана вручную, на остальных дорожках всё штатно.

## 2. Другой алгоритм контрольной суммы данных

**so.aim, copy.aim, vibu35.aim, JOKER.aim** — у каждого ровно **14 секторов**, и это
всегда одни и те же: **дорожка 0 секторы 16–20 и дорожка 1 секторы 0–8**, то есть
непрерывный логический блок в 3584 байта. Записанная сумма совпадает с **XOR** всех
256 байт:

```
so.aim, дорожка 0, сектор 16: записано $60
   сумма с переносом (Агат) = $1B
   XOR                      = $60   <-- совпало
контрольный сектор 15: записано $A0, сумма с переносом = $A0
```

Данные в этих секторах выглядят как шифрованные, в отличие от структурированных
соседей. Проверены восемь вариантов алгоритма (простая сумма, XOR, ROL+сумма,
ROL+XOR, другие затравки и длины) — совпадает только XOR, «необъяснённых» нет.

## 3. Дорожки, не являющиеся дорожками

### OA23 (дорожки 1–6) и OA27 (дорожки 1–9): сигнатура «KENT»

Секторов нет вообще. Внутри — DESYNC, сигнатура `CB C5 CE D4` (это `KENT` в кодировке
Агата, со старшим битом) и дальше сырой код 6502:

```
OA23, дорожка 1:
  [129]00/01 [130]AA*9 [139]00/01 [140]CB [141]C5 [142]CE [143]D4 [144]16 [145]38 [146]2E [147]4C ...
                                       K     E     N     T                            JMP
```

Та же подпись стоит и на дорожке 0 обоих дисков, перед первым сектором. `OA13.AIM`
из той же папки полностью чистый.

### VolgoUSN_01…11, дорожка 0

```
    141: DESYNC + FF 00 ...      <- двойной DESYNC: две метки через две ячейки
    143: DESYNC + AA AA ...
    325: DESYNC + адрес   vol=$00 trk=0 sec=0 эпилог=$A5
    338: DESYNC + данные
    627: DESYNC + адрес   vol=$01 trk=0 sec=1 эпилог=$A5
    640: DESYNC + данные
    907: DESYNC + AA AA ...      <- одиночная метка без марки
   1161: DESYNC + адрес   vol=$FE trk=90 sec=170 эпилог=$AA   <- мусор из неформатированной зоны
   1172: DESYNC + данные (сумма не сходится, эпилог $04)
   2012: импульс индексного отверстия (начало)
   2135: импульс индексного отверстия (конец)
   6201: КОНЕЦ ДОРОЖКИ, дальше 262 ячейки заполнения $FF
```

Два настоящих сектора вместо 21, двойной DESYNC как маркер, физически короткая
дорожка. Метки индексного отверстия (`$03`/`$13`) встречаются только на таких
дорожках и больше нигде во всей коллекции.

## 4. Одиночные маркеры

### CLOCKBADER, дорожка 7, ячейка 1848

Единственная аномалия на всём диске: лишний DESYNC с намеренно испорченной адресной
маркой (`95 7F` вместо `95 6A`) и подписью `42 54 61` = `BTa`. У самой ячейки DESYNC
байт данных `$AA`, а не обычные `$00`/`$A4`.

```
[1830]AA*18 [1848]AA/01 [1849]95 [1850]7F [1851]42 [1852]54 [1853]61 [1854]AA*2 [1856]00/01 [1857]95 [1858]6A ...
```

### MGR4_4, дорожка 2, сектор 10

DESYNC внутри поля данных, на 86-м байте из 256. Поле заканчивается штатно, и
контрольная сумма сходится:

```
[1342]AA [1343]A4/01 [1344]CD 84 3F 38 2F EE ...   ... [1513]сумма [1514]5A
```

Контроллер при обычном чтении на этом байте пересинхронизируется, и данные съезжают;
загрузчик защиты именно это и проверяет.

## 5. Особенности уровня формата AIM

### Команда `$81`

Не описана в спецификации из эталонного perl-скрипта (`$01` и `$80` — DESYNC, `$02` —
конец дорожки, `$03`/`$13` — индексное отверстие). Встречается ровно в позиции DESYNC
перед маркой данных, байт данных `$FF`, то есть это `$01|$80` — оба флага сразу:

```
M&S_12, дорожка 64: ... 5A FF AA*5 A4 [FF/81] 6A 95 <данные>
```

16 штук на дорожке 64 в `M&S_12.aim` и 5 на дорожке 55 в `M&S_15.aim`. Конвертер
`aim2hfe` раньше выдавал «unsupported AIM command 129» и терял метку — **исправлено**,
`$81` распознаётся как DESYNC.

### Нули в хвосте GAP'а

В `M&S_02…09` (все сняты 31.08.2010 одной версией дампера) последние 23 ячейки каждого
длинного GAP'а записаны нулями вместо `$AA`:

```
M&S_01:  ... 5A  AA*33                     DESYNC  95 6A
M&S_02:  ... 5A  AA*9 FF AA A4  00*23      DESYNC  95 6A
```

Картина одинакова на всех 1280 дорожках восьми дисков (`GAP total = 542` на каждой),
поэтому это почерк дампера, а не содержимое дискеты. `aim2hfe` считает такие ячейки
частью GAP'а и восстанавливает в `$AA`; до этого все восемь образов не
конвертировались вообще.

### Прочие регулярные мелочи

Не дефекты, а почерк форматтера конкретного диска: у M&S-дисков в GAP2 всегда стоит
`95 84`; у M&S_02…09 после каждого поля данных лишний байт `$FE`; у `copy.aim` после
эпилога идёт `AA AA 00 00 5A` — след стыка перезаписи.

### Volume ID

Первый байт адресного поля на разных дисках означает разное: `$7B` на дисках SpriteOS,
`$FE` на OA*/MGR4_4, `$FF` на части M&S. На дисках M&S и VolgoUSN он **равен номеру
сектора**. В `M&S_18` дорожки 0–16 имеют `$FF`, а у каждой из остальных дорожек своё
значение в диапазоне 0…20, постоянное внутри дорожки.

## 6. Физический порядок секторов

Большинство дорожек — простой поворот 0…20 (дамп начинается с произвольного угла),
это норма. Настоящие перестановки:

* **CLOCKBADER, дорожка 8**: `10,6,3,5,15,16,19,1,7,8,4,13,17,2,12,18,9,14,11,20,0` —
  при том что остальные 159 дорожек идут строго 0…20.
* `MGR4_4` — 17 дорожек с неповоротным порядком, `M&S_14` — 12, `M&S_11` — 12,
  `M&S_10` — 10, `M&S_12` — 9. Типичный вид `0..8, 12..20, 9,10,11`: кусок дорожки
  переписан отдельно, со своим стартом.

## 7. Что из этого следует для dsk_tools

Проверено: содержимое секторов, извлечённое из AIM (`aim_extract.py`), побайтово
совпадает с результатом `aim2hfe` → `fddconv` на всех 21 образах, где обе дороги
работают. Конвертер данные не теряет. Остальное:

1. **`aim2hfe` не конвертирует 4 образа** — `OA23`, `OA27`, `VolgoUSN_08`,
   `VolgoUSN_10`. Две разные причины: у OA23 дорожка 1 («KENT») пакуется в 6389 ячеек
   при `GAP total = 8` — ужимать нечем; у VolgoUSN дорожка 0 даёт 6208 ячеек, то есть
   **короче** 6250, её надо не сжимать, а дополнять. Сейчас и то, и другое — ошибка на
   весь файл. *Не исправлено.*
2. **HFE-загрузчик отвергает файл целиком из-за одной нестандартной дорожки.**
   `decode_agat_840_track` ставит `errors = true` на любой эпилог ≠ `$5A` и любое
   несовпадение суммы, `LoaderHXC_HFE::load` возвращает ошибку на весь образ, а
   `detect_fdd_type` превращает её в «Invalid HFE file format». Из 38 сконвертированных
   HFE 14 не открываются (все VolgoUSN, вся группа SpriteOS, MGR4_4), хотя исходный AIM
   открывается: `LoaderAIM` эпилоги и суммы просто игнорирует. *Не исправлено.*
3. **`decode_agat_840_track` мог выбросить исключение наружу** — после `iterate_until`
   шли `in.at(in_p++)` без проверки границы, и на `copy.aim` пользователь видел
   `__n (which is 6272) >= this->size() (which is 6272)`. *Исправлено:* обрезанное поле
   теперь считается повреждённой дорожкой.
4. **`LoaderAIM` игнорировал номер сектора** — писал секторы в физическом порядке
   подряд (`buffer[out_p++]`), да ещё и без границ дорожек. Для дисков, чей дамп
   начинается не с сектора 0, образ молча перемешивался: `CLOCKBADER` — вся дорожка 8
   (5360 байт), `M&S_13` — с дорожки 7 (416 637 байт), `M&S_16` — с дорожки 7
   (452 340 байт). *Исправлено:* разбор идёт по дорожкам, поля ищутся от метки DESYNC
   (включая `$81`), сектор кладётся по номеру из адресного поля, поле, переходящее через
   конец дорожки, дочитывается с её начала. Теперь раскладка совпадает с эталонной
   (`aim_extract.py`) на всех 42 образах, включая защищённые. Ошибка возвращается
   только если не найдено ни одного сектора, поэтому диски с нестандартными дорожками
   больше не отваливаются целиком.
5. Тот же незащищённый шаблон `iterate_until` + `.at()` есть в
   `LoaderHXC_HFE::file_info()` и `LoaderAIM::file_info()` (диалог свойств образа).
   *Не исправлено.*
6. **`detect_fdd_type` требует, чтобы первый байт нулевого сектора был `$01`** — иначе
   «Failed to load AIM file». На этой проверке спотыкаются 13 образов, которые
   загрузчик теперь читает правильно: у `VolgoUSN_01…11` там `$02`, у `OA23`/`OA27` —
   `$04`. С принудительным `-f a840:dos33` они читаются побайтово верно.
   *Не исправлено.*
